# Batch-invariant mode (`flashinfer.batch_invariant`)

`flashinfer.batch_invariant` provides deterministic, batch-invariant implementations of FlashInfer operators, selected
with the keyword `batch_invariant=True` on the operator's public API. The kernels are CuTe-DSL kernels generated by an
engine that fixes the order of every floating-point reduction and the exact instructions the kernels issue, tensor-core
instructions included; the reduction orders are proved in Lean and the generated kernels are checked bit for bit on the
device.

## The guarantee

With `batch_invariant=True` an output's bits depend on the input values and the fixed dimensions alone:

| | Property | Meaning |
|---|---|---|
| R1 | Run-to-run determinism | same inputs, same path: same bits, across processes, streams and CUDA-graph replay |
| R2 | Batch invariance | a row's bits do not depend on batch size, padding, position, neighbours or SM count |
| R3 | Configuration agreement | every configuration the dispatcher may pick gives the same bits |
| R4 | Cross-path agreement | the members of one class (for example the output layouts of a quantizer, or an fp32 input and its exact 16-bit widening) give the same bits |

Each class has one fixed dataflow, named and hashed into a **fingerprint**; `flashinfer.batch_invariant.fingerprint(op)`
returns it, scoped to (fingerprint, FlashInfer version, architecture). Bitwise equality is the acceptance criterion of
every test in `tests/batch_invariant`.

## Tests

```bash
pytest tests/batch_invariant -q
```

Device-free tests cover the backend rule, the fingerprints, dispatcher membership and the currency of the generated Lean
cases. On a supported device the tests check bitwise equality against the operator's reference backends, run-to-run
determinism including CUDA-graph replay, batch, permutation and sub-batch invariance, and the error contract.

## How to check the proofs

`lean/` proves that every placement of a block reduction computes the canonical tree, that the scales and codes derived
from it are bit-equal under any commutative interpretation, that the zero-filling kernels equal their specifications
under the restricted identity `fmax(v, +0) = v` for `v >= +0`, and the launch-model statements of R1 and R2
(`BIKernels/MXQuant.lean`). `Cases.lean` is generated from the Python specification and engine
(`python -m flashinfer.batch_invariant.lean_cases`); the Lean model reproduces the Python S-expressions node for node
by kernel `decide`, and `tests/batch_invariant/test_lean.py` byte-compares the committed file (the `lake` steps run when
the toolchain is installed).

Trust statement: **Lean's standard axioms (`propext`, `Classical.choice`, `Quot.sound`), plus `Lean.ofReduceBool` for
eight named decided table facts** (the two layout bijections, the three UE8M0 fact tables and the three generated UE8M0
conversion tables, whose `ue8m0Byte` goes through the well-founded `Nat.log2`). `Lean.ofReduceBool` trusts the compiled
evaluator for those closed Boolean terms; `lake exe axioms` enforces exactly this list and fails on any `sorry`.

```bash
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
export PATH="$HOME/.elan/bin:$PATH"            # the pinned toolchain is lean/lean-toolchain (leanprover/lean4:v4.15.0, no Mathlib)
cd flashinfer/batch_invariant/lean
lake build && lake build conformance axioms    # ~1 min cold
lake exe conformance | wc -l                   # 43 lines: the Lean model's terms for the generated cases
lake exe axioms
#   axioms check: 613 user declarations of BIKernels.*, 8 named table theorems decided by native_decide (Lean.ofReduceBool), 0 with sorry, 0 violations
```

The Lean steps are not run in CI. The `lean/` directory is part of the repository only: it has no `__init__.py` and
no package data entry, so no `.lean` file is in the wheel.

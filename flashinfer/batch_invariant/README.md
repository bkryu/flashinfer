# Batch-invariant mode (`flashinfer.batch_invariant`)

Deterministic, batch-invariant kernels behind one keyword, `batch_invariant=True`: CuTe-DSL kernels generated by an
engine whose reduction orders are proved in Lean and checked bit for bit on the device. This PR wires the first class,
`mxfp8.quant`, into `flashinfer.mxfp8_quantize`; further classes follow behind the same flag.

## The guarantee

With `batch_invariant=True` an output's bits depend on the input values and the fixed dimensions alone:

| | Property | Meaning |
|---|---|---|
| R1 | Run-to-run determinism | same inputs, same path: same bits, across processes, streams and CUDA-graph replay |
| R2 | Batch invariance | a row's bits do not depend on batch size, padding, position, neighbours or SM count |
| R3 | Configuration agreement | every configuration the dispatcher may pick gives the same bits |
| R4 | Cross-path agreement | the members of one class (here the three scale-factor layouts; fp32 inputs and their exact 16-bit widenings) give the same bits |

Each class has one fixed dataflow, named and hashed into a **fingerprint**; `flashinfer.batch_invariant.fingerprint(op)`
is the receipt, scoped to (fingerprint, FlashInfer version, architecture). Bitwise equality is the acceptance criterion
of every test.

## The flag

* Keyword-only `batch_invariant: bool = False` on the wired API; the default changes nothing for anyone.
* The batch-invariant kernel is reachable only through `backend="auto"`; `batch_invariant=True` with any other
  `backend` raises `ValueError`. `"auto"` without the flag behaves as the API's default (`mxfp8_quantize`: `"cuda"`).
* The mode never falls back: an unsupported shape, dtype, layout, device or architecture raises
  `BatchInvariantUnsupportedError` (a `ValueError`) naming the class and the limit.
* Architectures: SM100, SM103, SM107 (the tcgen05 parts). Elsewhere `batch_invariant=True` raises.

```python
q, sf = flashinfer.mxfp8_quantize(x, backend="auto", batch_invariant=True)   # x: bf16 / f16 / fp32, shape (..., K), K % 32 == 0
flashinfer.batch_invariant.fingerprint("mxfp8_quantize")                     # 'mxquant-mxfp8-9018bd1627b3e72a'
```

`mxfp8.quant` honours FlashInfer's contract for `mxfp8_quantize`: the three `SfLayout`s (128x4 / 8x4 swizzled,
linear), `alignment` padding, `enable_pdl`, outputs of the same shapes and bytes as the `cute-dsl` backend. The
dataflow is TransformerEngine's MXFP8 chain (`amax` over the exactly widened block, `cvt.rp.satfinite.ue8m0` of
`mul.rn(amax, fp32(1/448))`, the exact `2^(127-e8)` inverse at every byte, `cvt.rn.satfinite.e4m3` of `mul.rn`). It is
bit-identical to FlashInfer's `cuda` and `cute-dsl` backends except on blocks whose amax is below `448 * 2^-127`
(FlashInfer zeroes their codes, the class keeps the values) and on `-inf` elements (`-448` here, `+448` there); the tests
pin both. The dispatcher is a closed-form rule of (M, K, element bytes, SM count, layout); every pick is a member of
the enumerated space and the compiled kernel is never specialized on M.

## Tests

```bash
pytest tests/batch_invariant -q     # device-free: backend rule, fingerprint, dispatcher membership, Lean cases current;
                                    # on SM100 / SM103 / SM107: bitwise vs FlashInfer's backends over 3 layouts x 3 dtypes,
                                    # determinism + graph replay, batch / permutation / sub-batch invariance, the errors
```

## How to check the proofs

`lean/` proves that every placement of the block amax computes the canonical tree, that the scale and the codes are
then bit-equal under any commutative interpretation, that the zero-filling kernel equals the spec under the restricted
identity `fmax(v, +0) = v` for `v >= +0`, and the launch-model statements of R1 / R2 (`RLKernels/MXQuant.lean`).
`Cases.lean` is generated from the Python spec and engine (`python -m flashinfer.batch_invariant.lean_cases`); the
Lean model reproduces the Python S-expressions node for node by kernel `decide`, and `tests/batch_invariant/test_lean.py`
byte-compares the committed file on every CI job (the `lake` steps run when the toolchain is installed).

Trust statement: **Lean's standard axioms (`propext`, `Classical.choice`, `Quot.sound`), plus `Lean.ofReduceBool` for
eight named decided table facts** (the two layout bijections, the three UE8M0 fact tables, the three generated UE8M0
conversion tables, whose `ue8m0Byte` goes through the well-founded `Nat.log2`). `Lean.ofReduceBool` trusts the
compiled evaluator for those closed Boolean terms; `lake exe axioms` enforces exactly this list and fails on any `sorry`.

```bash
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
export PATH="$HOME/.elan/bin:$PATH"            # the pinned toolchain is lean/lean-toolchain (leanprover/lean4:v4.15.0, no Mathlib)
cd flashinfer/batch_invariant/lean
lake build && lake build conformance axioms    # ~1 min cold
lake exe conformance | wc -l                   # 43 lines: the Lean model's terms for the generated cases
lake exe axioms
#   axioms check: 613 user declarations of RLKernels.*, 8 named table theorems decided by native_decide (Lean.ofReduceBool), 0 with sorry, 0 violations
```

The Lean checks run by hand for now; a CI job follows once the project has a runner for it. The `lean/` directory ships
in the repository only (no `__init__.py`, no package data): no `.lean` file is in the wheel.

# Batch-invariant mode (`flashinfer.batch_invariant`)

`flashinfer.batch_invariant` provides deterministic, batch-invariant implementations of FlashInfer operators, selected
with the keyword `batch_invariant=True` on the operator's public API. The kernels are CuTe-DSL kernels generated by an
engine that fixes the order of every floating-point reduction and the exact instructions the kernels issue, tensor-core
instructions included; the reduction orders are proved in Lean and the generated kernels are checked bit for bit on the
device. The first operator is the bf16 GEMM, `flashinfer.mm_bf16`, on SM100 (B200), SM103 (B300) and SM107 (Rubin).

## The guarantee

With `batch_invariant=True` an output's bits depend on the input values and the fixed dimensions alone:

| | Property | Meaning |
|---|---|---|
| R1 | Run-to-run determinism | same inputs, same path: same bits, across processes, streams and CUDA-graph replay |
| R2 | Batch invariance | a row's bits do not depend on batch size, padding, position, neighbours or SM count |
| R3 | Configuration agreement | every configuration the dispatcher or the autotuner may pick gives the same bits |
| R4 | Cross-path agreement | the members of one class (for the GEMM: both weight layouts, and the workspace split and the in-CTA chunk fold of one chunk count) give the same bits |

Each class has one fixed dataflow, named and hashed into a **fingerprint**; `flashinfer.batch_invariant.fingerprint(op,
**dims)` returns it, scoped to (fingerprint, FlashInfer version, architecture). Bitwise equality is the acceptance
criterion of every test in `tests/batch_invariant`.

## `mm_bf16(a, b, backend="auto", batch_invariant=True)`

The flag replaces the backends with the batch-invariant class rather than adding a backend to them (a backend's kernel
is batch-variant, so the autotuner must never be free to pick one); it therefore requires `backend="auto"`. Inside the
class the autotuner is free: under `flashinfer.autotune(True)` it profiles the cost model's top configurations for the
shape, every one of which computes the same bits, so a tuned and an untuned process agree bit for bit and differ in
speed only. Without autotuning the dispatcher's cost model picks the configuration.

| Input | Accepted |
|---|---|
| `a` | `(M, K)` bf16, row-major (`K` a multiple of 8; any `M`, including 0) |
| `b` | `(K, N)` bf16: row-major, or the transpose of a row-major `(N, K)` weight (`N` a multiple of 8) |
| `out` / `out_dtype` | bf16 `(M, N)` row-major |
| `bias` | not supported (no fused epilogue) |
| `pdl` | accepted; the kernels run in plain stream order |

Anything else raises `flashinfer.batch_invariant.BatchInvariantUnsupportedError`, whose message names the class and the
limit. The mode never falls back to another kernel.

Two consistency classes exist, chosen by the weight shape alone (`gemm/schedule.py::chunks_for(N, K)`, a function that
takes no `M` by construction): `gemm.bf16.kfold`, one fp32 fold over the K steps of 16 from +0, and `gemm.bf16.kchunk[C]`
for weights too narrow to fill the machine, K cut into `C` chunks each folded from +0 and the partials folded in chunk
order. `fingerprint("mm_bf16", N=..., K=...)` identifies the class of a weight (`gemm-bf16-kfold-...` or
`gemm-bf16-kchunk<C>-...`); `M`, the configuration and the weight's layout do not enter it.

## Where the bits differ from the default backends

A batch-invariant class follows one specified dataflow; the default backends (cuDNN, cuBLASLt, CUTLASS, the CuTe-DSL
low-M kernels) each use their own accumulation order and change it with the shape, so the class is not bit-equal to any
of them, and they are not bit-equal to themselves across batch sizes: on Rubin, `mm_bf16(backend="cudnn")` at
`N = 2048, K = 8192` gives different bits for the same 64 rows at `M = 16` and `M = 300`. The class's rounding error is
of the size of cuBLAS's: the max norm-relative error against the exact product is within 10 % of `torch.matmul`'s at
every tested shape (`test_matches_reference`).

## Tests

```bash
pytest tests/batch_invariant -q
```

Device-free tests cover the fingerprints, the chunk rule, dispatcher membership, the tuner's tactic encoding and the
currency of the generated Lean cases. On a supported device the tests check the accuracy yardstick, run-to-run
determinism including CUDA-graph replay, batch, permutation and sub-batch invariance, agreement across weight layouts,
across the tuner's candidate configurations, between the two implementations of the split class and across persistent
grid sizes, autotuning (every candidate profiled, same bits during and after), and the error contract.

## How to check the proofs

`lean/` proves, for the opaque tensor-core step `mma16`, that the split kernel's index-addressed workspace and fixup
compute the chunked class for every chunk-to-CTA assignment, that the k-block pipeline of the mainloop equals the fold
for every stage count and block size, that no configuration, stage count or carried accumulator reaches a tile's
output (`config_invariance`, instantiated on the generator's whole configuration space), and the launch-model
statements of R1 and R2 (`BIKernels/GEMM.lean`, `BIKernels/GEMMConfig.lean`). What Lean cannot state is the hardware
hypothesis that every MMA instruction variant the space selects is the same per-element function; the GPU test
`test_config_agreement` checks it bit for bit. `Cases.lean` is generated from the Python specification and engine
(`python -m flashinfer.batch_invariant.lean_cases`): the Lean model reproduces the Python S-expressions node for node,
re-derives the chunk rule's table, checks every record of the configuration space against the knob constraints and
shows every dispatcher pick to be a member; `tests/batch_invariant/test_lean.py` byte-compares the committed file (the
`lake` steps run when the toolchain is installed).

Trust statement: **Lean's standard axioms (`propext`, `Classical.choice`, `Quot.sound`), plus `Lean.ofReduceBool` for
the named exhaustive checks over the configuration space** (`gemm_space_ok`, `gemm_space_c4_ok`,
`gemm_space_c4_cta_twins`, `gemm_dispatch_in_space`: hundreds of records each, decided by `native_decide`; every other
generated case is kernel `decide`). `Lean.ofReduceBool` trusts the compiled evaluator for those closed Boolean terms;
`lake exe axioms` enforces exactly this list and fails on any `sorry`.

```bash
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
export PATH="$HOME/.elan/bin:$PATH"            # the pinned toolchain is lean/lean-toolchain (leanprover/lean4:v4.15.0, no Mathlib)
cd flashinfer/batch_invariant/lean
lake build && lake build conformance axioms    # ~1 min cold
lake exe conformance | wc -l                   # 23 lines: the Lean model's terms and chunk counts for the generated cases
lake exe axioms
#   axioms check: 185 user declarations of BIKernels.*, 4 named table theorems decided by native_decide (Lean.ofReduceBool), 0 with sorry, 0 violations
```

The Lean steps are not run in CI. The `lean/` directory is part of the repository only: it has no `__init__.py` and
no package data entry, so no `.lean` file is in the wheel.
